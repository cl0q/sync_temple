# Phase 01.1: Token Persistence — Summary

## What was built

**Server (`main.go`):**
- New token resolution chain in `main()`: `--token` flag → `SYNC_TEMPLE_TOKEN` env var → `<dataDir>/.token` file → generate fresh 16-byte hex.
- Auto-generated tokens are persisted to `<dataDir>/.token` at mode 0600 (created with `os.MkdirAll(dataDir, 0755)` first if missing).
- Startup banner extended: when the token was persisted, the server prints `(persisted to <path> — restarts will reuse this)` so the user can see what happened.

**Client (`static/index.html`):**
- New module-level `auth401Handled` boolean guards the 401-storm path. Fires once per session.
- In `api()`, immediately after the `fetch` resolves and before any error throw, a 401 check: if `status === 401 && !auth401Handled && sessionStorage.sync_token` is set, the client clears the stale token, calls `uploadController.abort()` to cancel in-flight requests, hides both upload-progress containers, restores the auth gate with a red "Server rejected token — re-enter credentials" message, and refocuses the token input.
- `connect()` resets `auth401Handled = false` inside the `.then(...)` success branch so the next 401 (after the user re-enters a working token) re-arms the guard.

**Docs (`MANUAL.md`):**
- Paragraph added under the Token line documenting the resolution order, the `.token` file location, and a "keep it out of any tracked path" warning.

## Notes for Phase 1 UAT

After pulling this change, run the server with the data dir you actually use:
```
go run . --addr :8787 --data ./data
```
The first run prints both `Token:` AND `(persisted to ./data/.token)`. Copy the token into the browser. Subsequent Ctrl-C + restart cycles reuse the same token, so the browser session stays valid — the 401 storm cannot recur on simple restarts.

If you ever do hit a real 401 (e.g., from intentionally rotating the token file), the UI now reacts gracefully: ONE error message, focus on the token input, no console spam.
